# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A personal static website (`bladeinferior.github.io` / served from `/` on a custom domain — `index.html` picks the base path at runtime by checking `window.location.hostname`) with no build step, no bundler, and no framework. Every page is plain HTML with `<script>` tags (some `type="module"`, most not). There is no lint or test suite — `package.json` only lists `axios`/`node-fetch`, used by a handful of one-off Node scripts (see "Asset-download scripts" below), not by the site itself.

## Standing rules for every change

- **Keep this file up to date.** Any change to the site (new feature, changed behaviour, new file, new convention) gets a matching update here in the same turn. Don't wait to be asked.
- **Open the local site after a change.** The owner previews on VS Code's Live Server (`http://127.0.0.1:5500/`). If nothing is serving on port 5500, start a server there and open `collection-hub/collectionhub.html`. If something already is, leave it alone.

Both rules are also enforced by the project hooks in `.claude/settings.json` → `.claude/hooks/turn-guard.js`. `UserPromptSubmit` snapshots a hash of every uncommitted file. `Stop` compares against it, and if the turn changed anything it does two things. First, it opens the Collection Hub in the browser — starting `.claude/hooks/static-server.js` on port 5500 first if nothing is listening there (that fallback has no live reload, unlike Live Server, and keeps running until its node process is killed) — but only on the first changing turn of a session, or whenever it had to start the server itself; a server already running doesn't by itself prove a tab is open, but repeat opens on every turn would be worse, so a `claude-turn-guard-<session>.opened` marker in the OS temp dir remembers it already did this once this session. Second, it blocks the stop once, asking for a CLAUDE.md update, if CLAUDE.md wasn't among the changed files.

## Commands

- **Run the site locally**: just open the HTML files directly, or serve the repo root with any static file server (e.g. `npx serve .`) — there is nothing to build or compile first.
- **Run a one-off asset-download script** (from `collection-hub/`, where their `node_modules` lives): `node download-missing-pokeballs.js`, `node download-missing-trainers.js`, `node download-type-icons.js`. These are idempotent (they skip files that already exist locally) and only ever add new files under `collection-hub/`.
- No test runner, linter, or build command exists in this repo.

## Site structure

Top-level "hubs", each self-contained with its own `.html` pages, nav script, and (mostly) CSS:

- `collection-hub/` — Pokémon dex tracking, TCG cards, sleeves, pop figures, steelbooks, pins, game-completion tracking, milestones. By far the largest and most actively developed area.
- `quizhub/` — a live multi-player quiz builder/host/play system (`builder/`, `host-quiz/`, `join/`, `play-test/`, `engine/` for answer matching, `manage-quizzes/`, `review/`, `stats/`). `quiz-app-feature-spec.md` at the repo root is a standing backlog of specced-but-not-yet-built features for this hub — check it before assuming a described quiz feature exists.
- `movie-hub/` — a Letterboxd-watchlist picker wheel.
- `adminhub/` — owner-only tools: a Firestore-backed notes app (`notes.html`/`notes.js`), a local stream counter, and an imported achievement-walkthrough reader (`walkthroughs/walkthroughs.html`/`walkthroughs.js` — see "Achievement Walkthroughs" below).
- `homepage/` — assets for the root `index.html` landing page.

Root-level shared files used across multiple hubs: `firebase-config.js`, `admin-auth-core.js`, `admin-auth.js`, `navbar.html`/`navbar.css`, `scroll-to-top.js`, `sw-nocache.js`.

## Firebase: one shared app instance

`firebase-config.js` at the repo root is the **only** place that calls `initializeApp()` — it exports `db` (Firestore), `auth`, `googleProvider`, and `storage`. Every other `firebase-config.js` in the repo (`adminhub/firebase/firebase-config.js`, `quizhub/firebase/firebase-config.js`) is a thin `export * from '.../firebase-config.js'` re-export shim, not a second Firebase app — calling `initializeApp()` again with the same config throws, since `admin-auth.js` is loaded site-wide and would otherwise collide with a page's own second init. When adding a new Firebase-backed feature, import from the root config (directly or via the nearest shim) rather than initializing a new app.

## Admin auth (three layers, one identity)

- `admin-auth-core.js` — pure state/API (sign-in, `isSignedInAsAdmin()`, `onAdminStateChange()`), no DOM. Safe to import anywhere. `OWNER_EMAIL` is the single gate: only that Google account is ever treated as admin.
- `admin-auth.js` — wraps the core module and self-mounts the generic bottom-right sign-in widget site-wide.
- `adminhub/auth.js` (`requireAdminAuth()`) — a heavier full-page lockout gate + session pill, built on the same core module, used by pages under `adminhub/` (and conceptually by anything needing a hard "this whole page is admin-only" wall rather than just a corner widget).

All three resolve to the same signed-in identity, so signing in via one satisfies the others in the same browser. **Client-side gating is not real enforcement** — the actual security boundary is the Firestore/Storage rules requiring `request.auth.token.email == OWNER_EMAIL`, which live in the Firebase console, not in this repo. Adding a new admin-only Firestore collection or Storage path means updating those rules out-of-band.

## Collection Hub data model: localStorage + static JSON + Cloudflare export

Each collection type (pokedex, cards, sleeves, etc.) ships a static `*-backup.json` file in `collection-hub/`. On load, the page reads that JSON, then merges any `localStorage` edits on top of it as the live in-memory state — `localStorage` is the actual write buffer during editing, not the JSON file. The "Export" button (see `collections.js`, `pokedexes.js`, `completions/milestones.js`) POSTs the current state to a Cloudflare Worker, authenticated with the admin's Firebase ID token, which is what actually commits the updated JSON back to the GitHub repo. `unsaved-changes.js` tracks a dirty flag per dataset by diffing the current serialized state against the snapshot taken right after the localStorage merge (not against the raw fetched JSON), so edits from a prior unexported session aren't flagged as new changes on load.

That same Worker (`letterboxd-import.harrycummins.workers.dev` — the name reflects its original/primary purpose, the homepage's "latest film" widget and movie-hub's wheel, not this `/export` route specifically) is multi-purpose: `homepage/homepage.js` and `movie-hub/wheel/wheel.js` hit its `/`, `/watchlist`, and `/tmdb/movie` routes for Letterboxd data, while `/export` is the generic "commit this JSON file to GitHub" route every Export button (and `adminhub/walkthroughs.js`'s delete flow) uses — it isn't collection-hub- or pokedex-specific, it just takes `{filename, content}` plus the Firebase ID token and commits whatever's given. Its source isn't in this repo, same as the dedicated Worker "Achievement Walkthroughs" below uses — if it's ever renamed again, every one of its callers needs its hardcoded URL updated: `collection-hub/export-to-github.js`, `adminhub/walkthroughs/walkthroughs.js`, `homepage/homepage.js`, `movie-hub/wheel/wheel.js`.

**Cross-device reconciliation is three-way, not "local wins."** A device's `localStorage` only changes when that device itself edits something — it never expires — so a device left untouched for a while, then reopened, used to silently *revert* anything changed on other devices the moment it next exported: the old merge treated local as always current for any key it had at all, and Export just overwrote the whole backup file with that (possibly stale) local snapshot. This actually happened in production on 2026-09-29 (commit `0c1bce6` reverted `pokedex-backup.json`'s Cherish Dex/to-do flags that had been set days earlier). Fixed by `reconcileDict()`/`reconcileList()` in `unsaved-changes.js`: each load and each successful export persists a `<storageKey>__remoteBaseline` localStorage entry (`setRemoteBaseline()`) recording what the backup file actually looked like at that moment. On the next load, a field only stays on the local side if the device's current value for it actually differs from that baseline (a genuine unsynced edit) — otherwise the freshly-fetched backup's value wins, even over an existing local key. `pokedexes.js` uses `reconcileDict()` (dex data is `{ [pokemonKey]: {flags} }`); `collections.js` and `milestones.js` use `reconcileList()` (array of records keyed by the collection's title field, or `"name"`/`"id"`). Both fall back to the old local-wins-wholesale behavior for exactly one load on any device that has no baseline yet (i.e. hadn't been opened since this shipped). The baseline is set only from data confirmed to have actually reached GitHub (`export-to-github.js`'s `committed`/`unchanged` branches) — never from the manual-download fallback below, which is why that fallback (no admin token, or the Worker unreachable) now also `alert()`s instead of silently downloading a file while the UI acts like the export succeeded; that silent path was otherwise indistinguishable from a real sync from the owner's perspective. Any new per-device dataset with this same shape should reconcile through these same two helpers rather than reintroducing a bespoke local-wins merge.

## Pokédex filters (`collection-hub/pokedexes/pokedexes.js`)

All filter UI is built dynamically into an empty `#game-filter-container` div by `createFilterButtons()` — there's no static filter markup in `pokedexes.html` to edit. `applyFilters()` computes each filter as an independent `matchesX` boolean (search, game, generation, tags, missing/completion, type, etc.) and ANDs them together at the end; adding a new filter means adding both a UI section in `createFilterButtons()` and a `matchesX` const in `applyFilters()`, plus wiring its reset into the Reset Filters handler and `clearNonTodoFilters()`. Pokémon type data comes from `fullPokemonList.json`'s `type` field, a comma-separated string (e.g. `"Grass, Poison"`), parsed and lowercased at filter time — it is not pre-normalized in the JSON itself.

## Legends Z-A distortion data (`plza-distortions.json`)

Static `collection-hub/plza-distortions.json` maps a Pokémon's exact `fullPokemonList.json` name to an array of `{ star, mates }` objects — one entry per distinct Hyperspace Wild Zone cluster it spawns in, `mates` being every other pokemon Serebii lists sharing that same cluster (a cluster with nothing else in it still gets an entry with `mates: []`, needed so its star rating isn't lost). Scraped from Serebii's per-type `hyperspacewildzone/<type>.shtml` pages (plus `special.shtml` for Legendaries) by `collection-hub/download-plza-distortions.js` — a one-off script following the same manual-rerun convention as the other "Asset-download scripts" below, since Serebii updates these if a DLC wave adds more. Re-run it with `node download-plza-distortions.js` from `collection-hub/` any time the in-game distortions change; it logs any scraped name that doesn't match `fullPokemonList.json` so a mismatch (typo, missing regional form, newly-added Pokémon) can be caught by hand. Regional forms are only kept separate (e.g. "Alolan Marowak") when that exact name already exists in `fullPokemonList.json` — Serebii's icon filenames reuse the same letter-suffix convention for non-regional form variants too (Rotom's appliances, Vivillon's patterns), which this site doesn't track separately, so those collapse back to the plain species name instead of minting a form this site has no card for. A cluster's roster comes only from the "Spawns" table's `class="wildsprite"` images, not the "Focus" trio of icons above it — Focus is always a subset (Spawns also includes pre-evolutions Focus skips, e.g. Cubone alongside a spawned Marowak) — and the same real cluster can appear verbatim on more than one type page for a dual-type pokemon, so combos are de-duped page-to-page by `star + sorted(mates)` before being written out.

`pokedexes.js` derives two things from this. `getPlzaStars()` (sorted unique `star`s) feeds the card grid's own badge (`.plza-distortion-note`, set in `applyFilters()`) whenever `gameFilterState.plza === "include"`, regardless of which dex (if any) is being edited — outside that filter it isn't actionable, so it's hidden by default per-card either way. "🔀 Combinations" (`#plza-combos-btn`, in the Pokémon modal's `.modal-left`) is Shiny Dex only on top of that same filter — hunting new shinies is the one case it's actually useful for — shown only while `activeDexEdit === "shinyDex"` and `getPlzaCombosWithMates()` (combos with `mates.length > 0`, i.e. actually something to show) is non-empty for that pokemon. Click it and `#plza-combos-modal` lists one row per combo, each a small shiny-sprite+name card (`.plza-combo-card`, a shrunk-down version of the main grid's own card look — shiny since this whole feature is Shiny Dex only, see `getPokemonSpritePath(memberName, true)`), one per *other* pokemon in that distortion plus the searched-for one itself (picked out with `.plza-combo-card--self`, so it reads as part of the group rather than something to go remember). The button's own visibility is `updatePlzaCombosButtonUI()`, not just inline logic in `renderModalState()` — it also needs its own call from the "Legends ZA" game filter button and from Reset Filters, since toggling either while the modal is already open doesn't otherwise re-run `renderModalState()`, which would otherwise leave the button showing whatever it last was.

Each row is ordered by `orderPlzaComboMembers()`, not however `mates` happened to come out of the JSON: the searched-for pokemon's own evolution line first (itself before the rest of its line — a baby form like Igglybuff can have a *higher* Pokédex number than what it evolves into, so "itself first" can't just fall out of sorting the line by number), then every other line in the combo, each sorted by Pokédex number internally, the lines themselves ordered by their own lowest number (`plzaEvolutionFamily()` is `evolutionFamilies.json`'s entry for a name plus the name itself, since that file only ever lists the *others*). Number-within-a-line is a proxy for evolution stage, not the real thing, so an unrelated line that also happens to be numbered "backwards" is just left that way rather than guessed at.

While editing Shiny Dex specifically with that filter on, clicking a pokemon not yet shiny there (`!pokemonData.shinyDex`) jumps straight to its Combinations instead of doing nothing at all (its normal click behaviour there otherwise) — so checking what else can spawn alongside it never requires actually marking it shiny first. This shortcut sits in the card click handler, after the To Do block (so To Do's own click behaviour while browsing/Finding a to-do list is untouched) but before every other branch; it only fires when there's actually a combo to show, and leaves an already-shiny pokemon's click behaviour (opens the normal Shiny Dex modal) alone.

## Voice search (`collection-hub/voice-search.js`)

Loaded on every collection page; adds a 🎤 to `#search-row` (before `#clear-search`) using the browser's Web Speech API (no button at all where it's unsupported, e.g. Firefox). It just writes comma-separated terms into the input and fires its `input` event — every page's search already treats a comma as "match any", so no per-page wiring is needed. Continuous listening until clicked again or the word "stop" is said. Saying "back" removes the most recently added term without stopping the mic — handled the same as "stop" in the `recognition`'s `result` listener (acts on interim words too, not just once a phrase finalizes), except it `continue`s the loop instead of returning, and pops `terms` instead of ending the session. Neither word is ever itself added as a search term. Two matching modes, split on whether the page sets `window.voiceSearchNames`: the Pokédex does, so every spoken word is snapped to the nearest real Pokémon name (spelling distance, then a sound-alike key, plus regional-form handling like "Hisui and sligoo" → Hisuian Sliggoo) and unplaceable words show a red "didn't catch" notice; other pages only split out exact Pokémon names and keep everything else as heard (so "shiny" isn't "corrected" to Shinx). The pure matcher (`voiceSearchMatcher`) has no DOM and is `module.exports`-ed so it can be exercised from Node.

`attachVoiceSearch()` takes an optional `onListenChange(listening)` callback, fired at every point the mic actually starts/stops (both `micBtn` click paths, `stop()`'s other callers — spoken "stop", another mic starting, mic access denied). The main search bar's own call (bottom of the file, shared by every collection page) uses it to force the Pokédex's `#search-exact-toggle` on the moment dictation starts — voice terms are already snapped to real names, so exact matching stops e.g. "Onix" also pulling in every name that merely contains "on". It's deliberately only turned on here, not off when the mic stops (so the dictated results stay as they were once you stop talking) — it's `pokedexes.js`'s own `#clear-search` click handler and `#search`'s "input" listener that turn it back off, and only once the box is actually empty again (typed all the way back to nothing, same as clicking ✕). Other pages' `document.getElementById("search-exact-toggle")` is simply `null`, so the callback no-ops there.

On the Pokédex, `applyFilters()` (`pokedexes.js`) also reorders the grid to follow `searchTerms`' order (via CSS `order`, not DOM reordering) whenever there's a comma-separated search — most visibly, this makes voice search show Pokémon in the order they were spoken instead of dex order. Dex order (tracked as `dexIndex` while iterating `cardMap`, which is itself in dex order) is only the tie-break for cards sharing a term. Cleared back to plain dex order the moment the search box is empty, and skipped entirely in Page Mode, which pages by DOM index (`applyPagination`) and would desync from a purely visual reorder.

`window.attachVoiceSearch({ input, row, before, clearBtn, placeNotice })` adds another mic to any other input (the Pokédex's Add To Do modal uses it); only one mic dictates at a time, and `window.stopVoiceSearch()` stops whichever is on. On the Pokédex, `updateModeUI()` calls it, so any mode switch (Page/List/To Do/Find/Hunts, or changing dex) turns the mic off. The ▾ search-terms dropdown next to it is `createSearchTermsDropdown()` in `pokedexes.js`, shared by the main search bar and the Add To Do box.

## Pokédex modal layout (`shinyEditModeFlag`)

The Pokémon modal has two layouts: the normal all-dexes view, and Shiny Dex's variants/constraints view (`.shiny-edit-layout`, chosen in `renderModalState()`). `shinyEditModeFlag` must always equal `activeDexEdit === "shinyDex"`. The Edit-button handler derives it that way after every toggle. Setting it only when Shiny Dex itself is toggled on or off left it stuck on after switching straight from Shiny Dex to another dex, and every modal afterwards showed the shiny layout. The Reset Filters handler also clears it.

## Pokédex fixed side stack

`#search-wrapper` → `#search-evolutions-row` → `#import-export-controls` are stacked by `syncSearchControlsLayout()` (measured, not static), but `#item-count-label` (284px) and `#game-filter-container` (324px) below them sit at fixed `.pokemon-page` tops. Anything that makes the upper stack taller covers the count. So `#import-export-controls` is forced onto one line (`flex-wrap: nowrap`, buttons shrink), rather than letting 📋 Changes wrap onto a second row when it appears. On mobile, `#search-evolutions-row` (Include evos/regionals, Exact match) and `#custom-list-controls` drop out of this stack entirely into their own `createMobilePopout()` panels instead (see below) — `syncSearchControlsLayout()` skips positioning either one under `window.matchMedia("(max-width: 768px)")`, leaving them `width-sync-pending`-hidden for that pop-out to uncover instead. Without that guard, this function's own synchronous call on page load reveals them in their desktop fixed position well before the pop-outs (set up later, inside the async data-fetch `.then()`) get a chance to relocate them — a visible flash-then-relocate glitch on every load.

## Pokédex custom lists (`#custom-list-controls`)

These are the Add List / Save List / Load List buttons in the column left of the search stack. Add List adds the visible Pokémon to an in-memory `customListStaging`. Save List writes that to Firestore (`customPokemonLists`, owner-only rules set in the console). Load List puts saved lists back into the search bar. The ✕ beside Save List (`#custom-list-clear-btn`) empties `customListStaging` without saving anything. It is always visible and 2:9 against Save List's width (27px, pinned with `flex: 0 0 27px`); Save List shrinks to make room so the pair stays the column's width. On mobile the whole column is its own `createMobilePopout()` panel (🗂, `right: 128`), next to the ⚙ Filters and 📊 Dex Progress toggles.

`showCustomListConfirm(message, { yesLabel, noLabel })` (built for this feature's own "delete this saved list?" prompt, hence the name) is actually this whole page's one generic yes/no modal — a `Promise<boolean>` stand-in for `window.confirm()` that can't get silently auto-dismissed the way a real one can. Every other confirmation on the page (e.g. "📋 Changes"' Cancel All Changes) reuses the same modal/function with its own message and button wording rather than a second near-identical modal or a native `confirm()`. Its z-index (4200) is set above every `.stats-modal-overlay` (4000), not just its own `#custom-list-*` group (3000) — it needs to paint over whichever modal it was actually opened from, and Cancel All Changes opens it from on top of the "📋 Changes" modal (`.stats-modal-overlay`).

## Pokédex to-do cover

On Trade/Wonder Trade/PoGo/Shiny Dex, a Pokémon that's on that dex's to-do list but not yet caught there gets `.on-todo` (see `isUncaughtTodo()`), set in both `applyFilters()` and `updateCardHighlights()` — dimmed with a "📝 To Do" badge, same look as a pending Find pick, so a Missing search shows it's already lined up. It's purely visual (still counts as missing everywhere) and hidden while the To Do view/Find is active via `#box-container.todo-view`.

Adding to that list has two separate routes, both only on Trade/Wonder Trade/PoGo/Shiny Dex. "➕ Add To Do" (`#todo-add-btn`, only shown once the To Do filter itself is on) opens a typed/spoken-list modal (`#todo-modal`) — a second naming of pokemon, independent of whatever's on the main grid. "📝 Add Matches" (`#todo-add-matches-btn`, shown instead while the To Do filter is *off* and the main search box isn't empty) works off whatever's already visible on the main grid — the result of whatever search (typed or voice) and filters are already narrowing it down — rather than asking for the names again: `getTodoMatchCandidates()` takes `getVisibleCardNames()` (same visible-cards reasoning the Add List custom-list button uses) and keeps only the ones missing from the dex itself and not already on its to-do list, each offered as its own checkbox in `#todo-matches-modal` so only some of a search's results have to be picked, not all. `updateTodoAddMatchesButtonUI()` (called from the end of `applyFilters()`, plus everywhere else that can change `activeDexEdit`/`todoFilterActive`/`huntsModeActive` without otherwise reaching it) keeps the button's visibility in sync with both the search box and the candidate count. When there's only one candidate, clicking the button skips the checklist modal entirely and adds that one pokemon straight away (`addNamesToTodo()`, shared with the modal's own Add button) — nothing to actually choose between.

## Pokédex Reset Filters scope

Reset Filters clears search/game/generation/tag/type/missing/completion/constraint criteria and the To Do filter itself, but deliberately leaves `activeDexEdit` (which dex you're editing) and that dex's own edit-mode flags (`shinyEditModeFlag`, `pogoShinyModeFlag`, `huntsModeActive`) untouched — it narrows/un-narrows what's shown within whichever dex is already being edited, it doesn't back out of editing it altogether. `pageMode` is only forced off as a side effect of also resetting the To Do filter while Find (`todoFindActive`) was running, same condition `exitTodoFind()` itself guards on — Page Mode vs List Mode otherwise stays whatever the user had picked.

## Search bar self-clears when disabled

`#search-wrapper` gets `.filters-disabled` (opacity + `pointer-events: none`) while browsing a to-do list (`inTodoMode` in `updateModeUI()`) — which also makes it unclickable, so any leftover search text would be stuck showing with no way to reach `#clear-search` until it's enabled again. `updateModeUI()` clears `searchInput.value` (and re-runs `applyFilters()`) itself whenever it's about to apply that class, so this can't happen regardless of which path left text in the box.

## Shiny Hunts archive (`collection-hub/pokedexes/pokedexes.js`, Shiny Dex only)

A second, independent data domain living on the same page as the main per-Pokémon grid: `shinyHunts` is a flat array of `{ id, name, encounters }` records (own localStorage key `"shinyHunts"`, own backup file `collection-hub/shiny-hunts-backup.json`, own unsaved-changes tracker), not part of `savedDexData`. The "Hunts" button in `#page-controls` only appears while `activeDexEdit === "shinyDex"`; toggling it (`huntsModeActive`) swaps the whole per-Pokémon browsing UI out for `#hunts-container`'s own card grid (see the hunts-mode branch in `updateModeUI()`) rather than filtering on top of it the way To Do does. Add/Edit/Delete follow completions.html's Milestones tab pattern exactly (`.add-item-box` form modal + `.modal-left`/`.modal-right`/`.item-actions` view modal), reusing those global CSS classes. The single Export button commits **both** files in one click via a shared `exportJsonFile()` helper — any new per-page data domain that needs GitHub-backed persistence should follow this same "own tracker key, own backup JSON, exported alongside the rest" shape rather than being folded into `savedDexData`.

## Notes app (`adminhub/notes.js`)

Firestore collection `notes`, one doc per note (`title`, `content`, timestamps). `content` is a single newline-joined string, not structured JSON — each line encodes its own type via a bracket prefix: plain text is the raw line, checkboxes are `"[ ] text"` / `"[x] text"`, images are `"[img] <url>"`. The DOM mirrors this as one `.note-line` element per line inside `#note-content-input`; `serializeContent()`/`deserializeContent()` are the two directions of that encoding. Images upload to Firebase Storage under `notes/{noteId}/...` and only the resulting download URL is stored in the content string.

## Stream Counter (`adminhub/counter.html`/`counter.js` + `adminhub/stream-counter-server/`)

The one admin-hub feature that needs write access outside the repo, so unlike everything else here it can't run as a static page — `adminhub/stream-counter-server/server.js` is a standalone local Node/Express server (own `package.json`/`node_modules`, following the same "commit node_modules" convention as `collection-hub`'s asset-download scripts). It's started manually via `start-counter.bat` in that folder (double-click it, or a desktop shortcut to it) rather than run continuously — it's only needed the rare times a stream is happening, so there's deliberately no auto-start-at-login or background service. The `.bat` launches the server and then opens the browser straight to `adminhub/counter.html`; closing its console window stops the server. It double-duties as the static file server for the *entire* site (`express.static` on the repo root) so `counter.html`'s `fetch('/api/generate-counter')` calls stay same-origin — opening the page via GitHub Pages or any other static server instead means the buttons will fail, since only this server has the API route. `POST /api/generate-counter` drives Textcraft's real Pokémon-style generator (`gentext3.php`, with every style param hardcoded from a captured working request — only `text` ever changes) rather than recreating that look, downloads the resulting PNG, and atomically replaces `D:\Libraries\Desktop\leisure\streaming\currentNum.png` (write to `.tmp.png`, then rename) so OBS never reads a half-written file. The counter's current/total values live in the browser's `localStorage` only — the server is stateless per-request.

## Achievement Walkthroughs (`adminhub/walkthroughs/`)

Imported game achievement walkthroughs from TrueAchievements, read on-site in two modes instead of switching screens mid-game. Three pieces, because TrueAchievements sits behind a Cloudflare JS challenge — confirmed by a direct `curl` test returning 403 "Just a moment..." for any server-side request — so nothing in this repo (a Worker, a Node fetch) can ever read those pages; only an already-challenge-passed browser tab can. Two of the three pieces are deliberately **not** in this repo at all, same as the pre-existing `.../export` Worker (below) already wasn't — their source lives only in the external tool that runs it, since this repo is public and both sit right next to real secrets:

- **Capture** — a Tampermonkey userscript, source kept only in Tampermonkey's own editor (not this repo). Runs *on* trueachievements.com. One click on a walkthrough's overview page queues every linked section (in page order) into `sessionStorage`, then the script re-runs itself on each page load as Tampermonkey navigates through them, extracting that section's content (paragraphs/images/achievement cards/spoilers, classified by generic DOM-shape heuristics — there's no way to see TrueAchievements' real markup from outside a real browser tab, so this is a best-effort first guess, confirmed or iterated live via an on-page preview overlay shown for the very first captured section before the rest of the crawl is trusted). An achievement embed is detected by its `.ach-panel` class (confirmed real markup: `<div class="ach-panel"><a class="title" href="/a<id>/<slug>">Name</a><p>Description.</p>...icon, progress bar, unlock date, "N guides" link, platform-flag icons...</div>` — falls back to the "N guides" count badge or an `a[href*="/achievement"]` link for anything not matching that exact shape) rather than captured with an icon — just its name (from `a.title`) + description (from the sibling `<p>`, not the whole panel's text) combined into one step. The achievement-page URL never actually contains the substring "/achievement" (it's `/a<id>/<slug>`), which is why name extraction used to fall through to "whole panel's text for both name and description" — the same string shown twice. A short (≤5-word) text step is treated as a lead-in label rather than real content (`mergeShortHeadings()`) and merged into whatever step comes right after it as that step's `heading`, rendered as a small heading above it on the site rather than its own separate step to click through. TrueAchievements' own spoiler widget (confirmed markup: `<div class="spoiler"><a onclick="Spoiler_Reveal(this)">*** Spoiler - click to reveal ***</a><span class="spoiler" style="display:none">...payload...</span></div>`) becomes its own `spoiler` step wrapping whatever's extracted from that hidden payload (an image, in the confirmed case, but it's extracted the same recursive way regardless of what's actually inside) — the reveal link's own text is dropped, not kept as a text step. Getting the payload's image out correctly needed a general fix too: an inline tag (`<a>`, `<span>`, etc.) wrapping *only* an image — the spoiler payload's own `<a><img></a>`, but not unique to spoilers — used to lose that image entirely, since inline tags only ever contributed their `textContent`, which never includes images. Two more bits of chrome get stripped post-extraction: a lone "Top" link, and any "Table of Contents"/"Contents" heading plus whatever numbered-link list immediately follows it. Once the queue empties, it POSTs the whole thing to a dedicated Cloudflare Worker, authenticated with a shared secret (`X-Import-Key`) — not a Firebase ID token, since this script runs on a different origin with no access to this site's Firebase session.
- **Storage** — a second, separate Cloudflare Worker (source kept only in the Cloudflare dashboard, not this repo — deliberately not the pre-existing `.../export` Worker: that one turns out to **always** commit under a hardcoded `collection-hub/` prefix, confirmed the hard way when a Delete silently committed to a bogus `collection-hub/adminhub/walkthroughs/walkthroughs-backup.json` instead of the real file, since it was only ever built for collection-hub exports). This Worker has two routes, both committing to the one real path (`adminhub/walkthroughs/walkthroughs-backup.json`) via the GitHub Contents API:
  - `POST /import` — the Tampermonkey importer's own route, shared-secret authenticated (`X-Import-Key`, matching a constant in the userscript, never this repo) since that script runs on a different origin with no Firebase session to present. Upserts one walkthrough entry by `sourceUrl` (not a slug of the game's name — two listings could share a display name).
  - `POST /manage` — called by the website itself (`adminhub/walkthroughs.js`'s `commitWalkthroughsFile()`, e.g. its Delete button), authenticated by a *real* Firebase ID token this time, verified inside the Worker against Firebase's own public JWKS (`https://www.googleapis.com/service_accounts/v1/jwk/securetoken@system.gserviceaccount.com`) — checking the RS256 signature, issuer/audience against this site's Firebase project, and `email`/`email_verified` against `OWNER_EMAIL`, all by hand since `firebase-admin` isn't available in a Worker. Takes `{ content: [...] }` and overwrites the file with exactly that array — the website computes the new array client-side (e.g. filtered for a delete) and this route just commits whatever it's handed, same shape every other write here ends up in.

  The file itself is a plain array, same shape convention as every other `*-backup.json` in this repo: `[{ gameName, sourceUrl, importedAt, sections: [{ title, sourceUrl, steps: [{type:'text'|'image'|'achievement'|'spoiler', ...}] }] }]` — an `image` step is `{url, alt}`, an `achievement` step is `{name, description}` (no icon), a `spoiler` step is `{steps: [...]}` (itself an array of ordinary steps, usually just one image).
- **Reading** — `adminhub/walkthroughs/walkthroughs.html`/`walkthroughs.js` (gated by `requireAdminAuth()`, same as `notes.js`), the only piece actually in this repo. Just fetches that static JSON — no Firestore anywhere in this feature. Library → Outline → Reader, three panels toggled by `.hidden` rather than routing. A library tile's main click area resumes straight into saved progress if there is any, else opens the outline — there's no separate "Outline" button on the tile any more, since that was always just a slower way to reach one of those same two destinations. In the outline, clicking a section row itself (not just its explicit buttons) jumps straight into Step Through at that section's first step, since that's the default way most sections actually get read; "📖 Read" next to it stays as the explicit way to open Scroll mode instead, and both buttons `stopPropagation()` so clicking either doesn't also fire the row's own click. `section.title` already carries TrueAchievements' own numbering ("4.4 Spring Meadows" etc.) — the outline row and reader header show it as-is rather than prepending a second index on top, which used to double it up. While reading a whole section at once (Scroll mode only — Step Through already has its own Next/Back that cross section boundaries), a "Next Section →" button sits next to "← Outline" at the top, hidden on the walkthrough's last section, and clicking any step's own text jumps straight into Step mode at that exact step (`onClickText` in `renderStepElement()`/`openStepFromScroll()`) rather than always landing back on step 1. Step mode's `goToStep(offset)` mirrors `openAdjacentPokemon()` in `collection-hub/pokedexes/pokedexes.js`: walking off either end of a section moves into the next/previous section, so Next/Back read as one continuous walkthrough. Its mic is a small dedicated `SpeechRecognition` listener — not a reuse of `collection-hub/voice-search.js`'s matcher, which solves the unrelated problem of snapping spoken words to Pokémon names. "next"/"previous" move a whole step (same as the click/arrow-key nav); "back" and anything else said work on a *finer* grain, tracking how far into the current text step's own *words* (not sentences — a rewind needs to land mid-sentence, e.g. un-dimming just "cat" out of an already-read "The cat is strong") the reading-aloud has reached (`wordReadIndex`, reset on every step change). Any recognized speech that isn't an isolated command word is matched via `matchSpokenWords()` two ways, in order: first *forward* (a sliding window of the step's remaining words, word-overlap scored, checked across the *whole* rest of the step, not just the next word or two — reading aloud can legitimately skip/paraphrase ahead) — the *first* (nearest) window clearing the threshold wins, not whichever scores highest further ahead, so a word said once goes to its next real occurrence instead of possibly jumping past it to a later, better-scoring one. Only if nothing ahead matches does it look *backward*, for the most recent (closest-to-current, not the first) already-read occurrence of what was said, and rewinds `wordReadIndex` to just before it — so repeating a word that appeared earlier un-dims from its latest occurrence onward instead of advancing. Dimming itself is `.walkthrough-word`/`.walkthrough-word--read` (opacity only — nothing is ever hidden, so re-reading something already passed is still right there). "back" is its own thing, not a one-word undo of that tracking — `rewindCurrentSentence()` un-dims the *whole* most recently affected sentence (whether it had been read in full or only partway through), using `sentenceBoundaries()` (word indices ending in `.`/`!`/`?`, plus a final implicit boundary for whatever trailing words have no closing punctuation) purely to find that sentence's start — "previous" is what moving a whole *step* back is called now. A command only fires on a short, isolated utterance (≤2 words) specifically to reduce (not eliminate) the walkthrough's own text containing "back"/"next"/etc. mid-sentence from misfiring navigation while being read aloud. Reading position (`localStorage['walkthroughProgress:' + sourceUrl]`) saves on every step change, on leaving the reader, *and* on `beforeunload`/`pagehide` as a last-resort net — resume is fully automatic, there's no separate bookmark action, and the library tile surfaces it ("▶ Resume: Section N") without having to open the outline first. Every rendered `<img>` (image steps, including inside a revealed spoiler) sets `referrerPolicy = 'no-referrer'` — confirmed by direct testing that trueachievements.com 403s any image request carrying this site's Referer header specifically (a request with no Referer, or their own, succeeds), so without this every walkthrough image would silently fail to load. Clicking any walkthrough image enlarges it full-screen (`#walkthrough-zoom-overlay`/`#walkthrough-zoom-image`, click it or the backdrop to close) — the same click-to-enlarge pattern `collection-hub/collections.js`'s `#image-zoom-overlay` already uses elsewhere on the site, redefined locally here per the hub-self-containment rule rather than imported. A `spoiler` step renders as its own collapsed "🔒 Spoiler — click to reveal" toggle (`renderStepElement()` recurses into its own `steps` once expanded) — same interaction TrueAchievements' own widget has, just rebuilt here since the original markup/JS doesn't come along with the capture.
- **Deleting** a walkthrough is the one write the *website itself* makes — `commitWalkthroughsFile()` in `walkthroughs.js` filters the array client-side and POSTs the result to the dedicated Worker's `/manage` route (above) with `getAdminIdToken()`.
- This page sits one folder deeper than every other adminhub page (`adminhub/walkthroughs/walkthroughs.html` vs e.g. `adminhub/notes.html`), which is why `adminhub/admin-nav.js` anchors its `navbar.html`/`sw-nocache.js` paths to `document.currentScript.src` rather than a plain relative path — same fix `collection-hub/collection-nav.js` already needed once collection-hub stopped being one consistent depth everywhere.

## Mobile pop-out pattern (`collection-hub/mobile-popout.js`)

`createMobilePopout()` doesn't build a separate mobile UI — it *relocates* the real, already-wired desktop controls (e.g. the whole `#game-filter-container`) into a floating panel below a toggle button on narrow screens, moving them back to their original DOM position above the mobile breakpoint. Returns a `sync()` function that must be re-called if the tracked container gets rebuilt (e.g. `createFilterButtons()` re-running). Only one panel can be open at a time across the page. The Pokédex has four: ⚙ Filters (`right: 16`), 📊 Dex Progress (`right: 72`), 🗂 Custom Lists (`right: 128`), 🔎 Search Options (`right: 184`, `#search-evolutions-row` — Include evos/regionals, Exact match). Any element handed to `createMobilePopout()` this way needs its *own* desktop-positioning code (if it has any, e.g. `syncSearchControlsLayout()`) to skip it on mobile too — see the fixed-side-stack note above for why.

## Service workers

Two independent service workers with non-overlapping concerns, resolved by scope specificity (the more specific scope always wins): `collection-hub/sw.js` (registered from `collection-nav.js`, scope `collection-hub/`) precaches an offline app shell for that hub specifically; root `sw-nocache.js` (registered from `index.html`, `quiz-nav.js`, `admin-nav.js`, scope `/`) does no caching at all — it just forces every other page to always re-fetch from the network instead of trusting the browser's HTTP cache, so deploys show up without a hard refresh.

## Asset-download scripts

One-off Node scripts under `collection-hub/` (`download-missing-pokeballs.js`, `download-missing-trainers.js`, `download-type-icons.js`) pull sprite/icon images from the PokeAPI sprites GitHub raw CDN (`raw.githubusercontent.com/PokeAPI/sprites/...`) into local folders (`cards/pokeballs/`, `icons/types/`, etc.). They're run manually, never part of any automated build, and are all written to skip files that already exist so they're safe to re-run.

`download-plza-distortions.js` is the odd one out in this list — it scrapes HTML (Serebii's Legends Z-A Hyperspace Wild Zone pages) and regenerates a data file (`plza-distortions.json`) rather than skip-if-exists-downloading images, since the whole point of re-running it is to pick up changes to that data. See "Legends Z-A distortion star ratings" above.
